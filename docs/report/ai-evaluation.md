## 1. สถาปัตยกรรม AI

### 1.1 หลักคิด: code ตัดสินใจ, LLM พูด

ปัญหาหลักของห้องติวที่ใช้ LLM ทั้งหมดคือ ทดสอบไม่ได้และอธิบายไม่ได้ว่าทำไมระบบเลือกสอนหัวข้อนั้นหรือให้คะแนนแบบนั้น "อ่านยัง?" จึงแยกหน้าที่ชัดเจน (ai-orchestration §1.3):

| ส่วน | ใครตัดสิน | ตัวอย่าง |
|---|---|---|
| ลำดับการสอน, หัวข้อถัดไป, ดาวความสำคัญ, ระดับความเข้าใจ (mastery), AI Buddy จะพูดไหม | **code** (Python ที่ test ได้ ใน `apps/api/app/domain/` · เทอม 1 มีแล้วคือ merge rules ของ checker · สูตรดาวทดลองใน `poc/P3/stars.py` · ที่เหลือมี spec แล้ว implement ใน S4 และเทอม 2) | ดาวคิดจากสัดส่วนข้อสอบเก่าที่หัวข้อนั้นออก (§2.3.5) · mastery คิดด้วย BKT (หัวข้อ 4) |
| คำตอบคณิตถูกหรือผิด และผิดตั้งแต่บรรทัดไหน | **SymPy** (math engine) | เทียบทีละบรรทัดว่าเท่ากับบรรทัดก่อนหน้าไหม (หัวข้อ 3 · P2) |
| ผิดแบบไหน, ประโยคที่ใช้อธิบาย, คำพูดของ tutor | **LLM** | `sign` เพราะ −3 กลายเป็น +3 |

code ส่ง **directive** (คำสั่งว่า turn นี้ต้องทำอะไร) ให้ LLM แปลงเป็นคำพูด · LLM ไม่ได้เลือกแผนการสอนเอง จึงไม่หลุดแผนเมื่อบทสนทนายาว และทุกการตัดสินใจ test ได้ด้วย unit test (เทอม 1 มี test ของ merge rules และ SymPy service · ส่วนอื่นเพิ่มเมื่อ implement)

### 1.2 AI ไม่เขียน database เอง

LLM คืนผลเป็น structured output (JSON ตาม Pydantic schema) หรือ action จาก whitelist เท่านั้น · ตอนนี้ทำแล้วกับตรวจคำตอบ (`CheckAnswerResult` ผ่าน gateway ที่ validate schema แล้วจึงเข้า merge rules) · ส่วนการแก้ขอบเขตด้วยแชท ออกแบบไว้ให้ LLM คืน action เช่น `set_importance`, `exclude` แล้ว code ตรวจว่า id มีจริง ค่าอยู่ในช่วง และ op อยู่ใน whitelist ก่อน apply (§2.3.6 · ยังไม่ได้ implement) · ป้องกันทั้ง hallucination และ prompt injection ที่พยายามให้ AI แก้ข้อมูลเอง

### 1.3 AI Gateway เดียว

ทุก AI call ในระบบผ่านฟังก์ชันเดียว `ai.call(purpose, input, schema)` (`apps/api/app/ai/gateway.py` · AI-01) ซึ่งทำ 5 อย่าง:

1. โหลด prompt ตาม version ที่ระบุใน `config/ai.yaml`
2. เลือก model ตาม **tier** ของงาน (small, mid, main, vision, embed) · เปลี่ยน provider ได้โดยแก้ config ไม่ต้องแก้ code (AI-02)
3. ตรวจ output กับ schema และ retry พร้อมแนบ error เมื่อไม่ผ่าน (AI-05)
4. retry เมื่อ provider ล่มหรือ timeout หลัง backoff
5. บันทึก token, latency และสถานะของทุก call (AI-04)

ผลที่ได้: test ทั้งหมดใช้ **fake provider** ที่ตอบคงที่ (AI-03) จึงรันได้ใน CI โดยไม่มีค่าใช้จ่าย · ส่วนการวัดกับ model จริงแยกเป็น eval (หัวข้อ 2)

model ที่เลือกมาจากผล PoC (`config/ai.yaml` 1.3):

| tier | model | ที่มา |
|---|---|---|
| vision (อ่านลายมือ) | `gemini-3.5-flash-lite` | P1: อ่านถูก 95.2% ของบรรทัด |
| mid (สกัดหัวข้อ, ตรวจคำตอบ) | `gemini-3.5-flash` | P3: flash-lite หยาบเกินสำหรับสกัดหัวข้อ |
| embed (ค้นเนื้อหา) | `gemini-embedding-2` ที่ 768 มิติ | P3b: หาหน้าคำตอบเจอใน 4 อันดับแรก 19/20 |

gateway เรียก Gemini ได้ 2 ทางโดยไม่ต้องแก้ business logic: Gemini API (API key · ใช้ตอน PoC แรกๆ) และ Vertex AI (provider `vertex` · credential จาก ADC ไม่มี key file · PR #87) · ค่าใน `config/ai.yaml` ชี้ไปที่ Vertex ทุก tier

ฉบับ lite ที่ใช้ในเทอม 1 ยังไม่มี fallback ไป provider ที่สอง, circuit breaker และการเขียน log ลงตาราง `ai_calls` (แผนของเทอม 2)

### 1.4 Prompt เป็นไฟล์ที่มี version

prompt ทุกตัวอยู่ใน `prompts/<purpose>/v<n>.md` ไม่ใช่ string ในโค้ด · แก้ prompt = สร้าง version ใหม่ ไม่แก้ไฟล์เดิม แล้วรัน eval เทียบกับ version เดิมใน PR เดียวกัน (`prompts/README.md`) · ทำให้ย้อนดูได้ว่าตัวเลขใน report วัดจาก prompt ไหน

**ข้อมูลของผู้ใช้เป็นข้อมูล ไม่ใช่คำสั่ง:** เนื้อหาจากชีท ข้อสอบ และคำตอบของนักศึกษาอยู่ใน `<document>…</document>` เสมอ และ prompt บอก model ว่าข้อความในนั้นห้ามทำตาม · มี test ยืนยันว่าข้อความอย่าง "ignore previous instructions" ในคำตอบอยู่ใน `<document>` เท่านั้น (`test_check_answer_pipeline.py`)

### 1.5 ตัวอย่าง: ตรวจคำตอบ 1 ข้อ

ตัวอย่างนี้แสดงหลักทั้งหมดข้างบนในงานเดียว (ai-orchestration §2.4 · PR #68, #75, #80)

โจทย์: หา d/dx (x² sin x) · นักศึกษาเขียน 3 บรรทัด และบรรทัดที่ 3 ผิดเครื่องหมาย

1. **SymPy** คำนวณค่าของทุกบรรทัด (รวมการหาอนุพันธ์) แล้วเทียบกับบรรทัดก่อนหน้า → บรรทัด 3 ไม่เท่ากับบรรทัด 2 · คำตอบสุดท้ายไม่เท่าเฉลย
2. **code** ลองกลับเครื่องหมายทีละพจน์ในบรรทัด 3 แล้วพบว่าถูก → ส่ง hint `sign_flip_detected: line 3`
3. **LLM** (`check_answer`) ได้ผล SymPy เป็นประโยคสั้น + hint แล้วตอบว่า error type คือ `sign` พร้อมหลักฐานภาษาไทย 1 ประโยค
4. **merge rules** (code) รวมผล: ถูกหรือผิดและบรรทัดที่ผิดมาจาก SymPy · ประเภทความผิดมาจาก LLM · ถ้า LLM บอกว่าถูกแต่ SymPy บอกว่าผิด เชื่อ SymPy และบันทึกว่าขัดกัน
5. ผลลัพธ์ "ยังไม่ถูก · บรรทัด 3" แสดงในห้องติว (หน้าจอ PR #78) · ขั้นที่ tutor อธิบายวิธีแก้ทันทีออกแบบไว้แล้ว แต่ยังไม่ได้ต่อ checker เข้ากับห้องแชท (S3–S4)

ถ้า SymPy ตรวจคำตอบนั้นไม่ได้ (เช่น implicit differentiation หรือใช้เวลาเกิน 2 วินาที) LLM จะตัดสินแทนพร้อมค่า confidence (ทำแล้ว · P2 วัดได้ 5/5) · การให้ผู้ใช้แย้งผล (AM-12) ออกแบบไว้แต่ยังไม่ได้สร้าง

## 2. วิธีวัดผล

### 2.1 สองแบบของการทดสอบ

หลักในหัวข้อ 1.1 ทำให้แยกการทดสอบออกเป็น 2 แบบได้ชัด (`specs/system/test-strategy.md`)

| | ส่วนที่ code หรือ SymPy ตัดสิน | ส่วนที่ LLM ทำ |
|---|---|---|
| วัดด้วย | unit test ที่ผลต้องตรงทุกครั้ง | **golden set**: ชุดตัวอย่างที่คนเฉลยไว้ แล้ววัดเป็น % เทียบกับเป้า |
| ตัวอย่าง | merge rules, SymPy service (มีแล้ว) · สูตรดาว `compute_importance` (S4) | อ่านลายมือ, สกัดหัวข้อ, จำแนกประเภทความผิด |
| รันเมื่อ | ทุก PR ใน CI · ใช้ fake provider ไม่มีค่าใช้จ่าย | ทุกครั้งที่เปลี่ยน prompt หรือ model · รันมือในเทอม 1 แล้วแนบผลใน PR |
| เกณฑ์ | ทุก acceptance criteria ใน feature spec มี test ที่ชื่อขึ้นต้นด้วย requirement ID | เป้าจาก spec ของ PoC (`specs/poc/README.md`) ไม่ได้ตั้งหลังเห็นผล |

ทุก feature เดินตาม spec → test → code: เขียน spec ที่มี acceptance criteria แบบ Given/When/Then → สร้าง test จาก criteria → คน review test ก่อน → จึงเขียนโค้ดจน test ผ่าน · test ที่ review แล้วห้ามแก้โดยไม่ถามคน review

### 2.2 Golden set

| ชุด | ใช้กับ | ข้อมูล | คนเฉลย |
|---|---|---|---|
| ลายมือ (`evals/handwriting/`) | P1 อ่านลายมือ | 30 รูป 125 บรรทัด จาก 5 คน (คนละ 6 รูป) บน tablet · 8 รูปตั้งใจเขียนผิด เพื่อดูว่า AI แอบแก้ให้ถูกไหม · ทุกคนให้ความยินยอม | May พิมพ์ LaTeX รายบรรทัด |
| หัวข้อ (`evals/topics/mth10101/`) | P3 สกัดหัวข้อและดาว | MTH10101 ชีท 4 ไฟล์ 179 หน้า · ข้อสอบกลางภาคสแกน 2 ชุด 43 ข้อย่อย · คำถามค้นเนื้อหา 20 ข้อ | หัวข้อ 27 หัวข้อ + ดาว + map ข้อสอบ: May + Jam · คำถาม 20 ข้อ: May |
| คำตอบ (`evals/answers/`) | P2 ตรวจคำตอบ | 50 คำตอบ: 30 จากรูปลายมือ + 20 แบบพิมพ์ที่เขียนให้ครบทุกประเภทความผิด · expression 30, equation 11, factored 9 | AI ร่าง label ตามคู่มือ (ทีมตกลง · PR #52) แล้ว May ตรวจยืนยันทุกข้อ |

**คู่มือ label** (`evals/README.md`) เขียนก่อนเก็บข้อมูล เช่น ลายมือต้อง "พิมพ์ตามที่เขียน รวมถึงที่ผิดด้วย" · ประเภทความผิดถามเป็นลำดับ 6 ข้อ ข้อแรกที่ตอบ "ใช่" คือคำตอบ · prompt ของ `check_answer` ใช้กติกาชุดเดียวกัน LLM จึงตัดสินด้วยเกณฑ์เดียวกับคน label

**คน label ต้องไม่ใช่คนทำ PoC** เพื่อไม่ให้เฉลยเอนตามระบบที่ตัวเองสร้าง · มี 2 ข้อยกเว้นที่ทีมตกลงและบันทึกไว้ ซึ่งต้องนำมาคิดตอนอ่านผล:

1. label หัวข้อของ P3 มี Jam (คนทำ PoC) ร่วมทำ
2. label คำตอบของ P2 ร่างโดย AI เพราะเวลาไม่พอ แล้ว May (ไม่ใช่คนทำ P2) ตรวจและยืนยันทุกข้อ · ถ้า LLM ของ checker คิดแบบเดียวกับ AI ที่ร่าง label ตัวเลขอาจสูงเกินจริง

### 2.3 Metric และเป้า

| PoC | Metric | นับว่าตรงเมื่อ | เป้า |
|---|---|---|---|
| P1 | line accuracy | บรรทัดที่อ่านได้เท่ากับเฉลย**ทางคณิตศาสตร์** (ตัดสินด้วย SymPy) · จับคู่บรรทัดด้วย longest common subsequence | ≥ 80% |
| P1 | จับบรรทัดที่อ่านผิดด้วย confidence | มี threshold ที่จับได้ ≥ 95% | มีอย่างน้อย 1 ค่า |
| P3a | หัวข้อตรง | ช่วงหน้าของหัวข้อทับกับ label ≥ 0.5 (IoU) | ≥ 80% |
| P3a | ★★★ ตรง | หัวข้อ 3 ดาวตรงกับ label | ≥ 80% |
| P3b | recall@4 | chunk ที่ครอบหน้าคำตอบอยู่ใน 4 อันดับแรก | เลือกตัวที่ดีที่สุด |
| P2 | verdict | ตรงกับ label ทั้ง 4 ค่า (ถูก, ถูกแต่มีบรรทัดผิด, ยังไม่อยู่ในรูปที่สั่ง, ผิด) · ตัวหาร 50 | ≥ 95% |
| P2 | error type | ตรงกับ label · ตัวหาร 28 ข้อที่ไม่ถูก | ≥ 80% |
| P2 | บรรทัดแรกที่ผิด | ตรงกับ label · ตัวหาร 24 ข้อที่มีเลขบรรทัด | ≥ 85% |

เป้าของ P2 มาจากการคำนวณว่าใน 1 session ตอบประมาณ 20 ข้อ verdict 95% แปลว่าตัดสินผิดประมาณ 1 ครั้งต่อ session ซึ่งรับได้เพราะผู้ใช้แย้งผลได้ (learning-model §8)

### 2.4 ทำซ้ำได้

ทุก PoC มีคำสั่งรันซ้ำใน report (1–2 คำสั่งต่อการวัด) · ผลเก็บเป็นไฟล์ตัวเลขและ id ใน repo แต่ไม่เก็บข้อความจากชีทหรือรูปลายมือ · รายงานตัวเลขพร้อมขนาดตัวอย่าง (n) เสมอ · ระบุ prompt version และ model ที่ใช้จริง

## 3. ผล Proof of Concept

PoC แต่ละตัวตอบคำถามเสี่ยงข้อเดียวก่อนสร้างระบบจริง และตั้งทางเลือกสำรองไว้ล่วงหน้าเผื่อไม่ผ่าน (`specs/poc/README.md`) · report ฉบับเต็มอยู่ใน `specs/poc/reports/`

### 3.1 สรุป

| PoC | คำถาม | ผล | การตัดสินใจ |
|---|---|---|---|
| P1 | Vision LLM อ่านลายมือคณิตเป็น LaTeX ได้แม่นพอไหม | ความแม่น **PASS** (95.2%) · confidence แยกบรรทัดที่อ่านผิด **FAIL** | ใช้ `gemini-3.5-flash-lite` · **เปลี่ยน design:** ให้ผู้ใช้ยืนยันผลอ่านทุกครั้ง |
| P3a | สกัดหัวข้อจากชีทภาษาไทยได้ตรงกับคนไหม | **FAIL** (หัวข้อตรง 1/27 ด้วย flash-lite) · สูตรดาว **PASS** (10/12) | ใช้ fallback: ปรับ prompt และวัดใหม่บน Vertex AI |
| P3b | embedding ตัวไหนค้นเนื้อหาภาษาไทยได้ | `gemini-embedding-2` ที่ 768 มิติ recall@4 **19/20** | เลือกตัวนี้ |
| P2 | SymPy + LLM ตรวจคำตอบได้ตามเป้าไหม | **PASS** ทั้ง 3 เป้า: verdict 50/50, error type 27/28 (96.4%), บรรทัดแรกที่ผิด 24/24 | ใช้ pipeline SymPy → `check_answer/v1` → merge rules · error type 6 แบบตาม AM-06 ไม่ต้อง fallback |

### 3.2 P1 · อ่านลายมือ (n = 30 รูป, 125 บรรทัด)

- อ่านถูก 119/125 บรรทัด = **95.2%** (เป้า ≥ 80%) · รายคน 84.6–100% · เฉลี่ย 3.0 วินาทีต่อรูป
- บรรทัดที่อ่านผิดทั้ง 6 บรรทัดมี confidence 0.85–0.98 · ไม่มี threshold ใดที่จับได้ ≥ 95% · **model บอกความมั่นใจของตัวเองแบบเชื่อถือไม่ได้**
- 1 ใน 8 รูปที่ตั้งใจเขียนผิด AI แก้ให้ถูกเอง (`16x^{2}` → `12x^{2}`) ทั้งที่ prompt สั่งห้าม · ถ้าไม่มีคนเห็น คำตอบที่ผิดจะถูกตรวจว่าถูก
- **ผลต่อ design:** ทีมตกลงให้ระบบแสดง "อ่านได้แบบนี้ ถูกไหม" ทุกครั้ง (AM-02 · `ocr.always_confirm: true`) แทนการถามเฉพาะบรรทัดที่ confidence ต่ำ · เป็นตัวอย่างของหลัก human-in-the-loop ที่จุดเสี่ยง (ai-orchestration §1.3 P6)

### 3.3 P3 · เอกสาร → หัวข้อ + ดาว (MTH10101)

- **P3a ไม่ผ่าน:** `gemini-3.5-flash-lite` แบ่งหัวข้อหยาบเกินไป (ชีท 140 หน้าได้ 5 หัวข้อ ขณะที่ label มีประมาณ 22) จึงตรงกับ label แค่ 1/27 · `gemini-3.5-flash` แบ่งได้ละเอียดกว่า (ขั้นแรกตรง 15/27 = 56%) แต่ขั้นรวมหัวข้อไม่ได้คำตอบที่ใช้ได้บน free tier (503 ใน 18 จาก 20 call)

### 3.4 P2 · ตรวจคำตอบ (n = 50 คำตอบ)

- **ส่วน SymPy + merge rules** (PR #75): ตัดสินได้ 45/50 ข้อ ถูก/ผิดตรงกับ label ทั้ง 45 ข้อ · บรรทัดแรกที่ผิดตรง 20/22 · median 0.14 วินาทีต่อข้อ (ช้าสุด 0.44 วินาที จาก budget 2 วินาที)

- **pipeline เต็ม** (SymPy → `check_answer/v1` บน Vertex AI `gemini-3.5-flash` → merge rules · รันรอบเดียวครบ 50 ข้อ 31 ต.ค. · PR #80): verdict **50/50 = 100%** (เป้า ≥ 95%) · error type **27/28 = 96.4%** (≥ 80%) · บรรทัดแรกที่ผิด **24/24 = 100%** (≥ 85%) · ผ่านทั้ง 3 เป้า

- **ข้อที่พลาดข้อเดียว:** นักศึกษาแทน ∞ ลงในลิมิตตรงๆ · label ว่า "เลือกวิธีผิด" แต่ LLM ตอบ "ความรู้พื้นฐาน" · ตามคู่มือ label ข้อนี้ก้ำกึ่ง · ไม่แก้ label หลังเห็นผล และรอคนที่ไม่ใช่คนทำ PoC ตัดสิน (ถ้าเปลี่ยน label error type จะเป็น 28/28)

## 4. งานวิจัยรองรับ learning model

learning model คือส่วนที่ code ใช้ตัดสินว่าผู้เรียนรู้หัวข้อแค่ไหน, เมื่อไหร่นับว่าผ่าน, เรียนอะไรต่อ และทวนเมื่อไหร่ · สูตรทั้งหมดอยู่ใน `specs/system/learning-model.md` และรายการงานวิจัยที่ตรวจแล้วอยู่ใน `docs/research/learning-path.md` · หัวข้อนี้สรุปว่าการตัดสินใจหลักแต่ละข้อมีงานวิจัยใดรองรับ และข้อใดที่งานวิจัยท้าทาย

### 4.1 ตัวเลขทุกตัวต้องบอกที่มา

|---|---|---|
| [A] | มีงานวิจัยรองรับ | 7 |
| [calc] | คำนวณจากค่าอื่นหรือจากสูตร | 14 |
| [C] | ค่าเริ่มต้นชั่วคราว พร้อมวิธี calibrate และเมื่อไหร่ | 23 |

### 4.2 Mastery: Bayesian Knowledge Tracing

**เลือก:** BKT (Corbett & Anderson 1995) ประเมินความน่าจะเป็นที่ผู้เรียนเข้าใจหัวข้อ อัปเดตหลังทุกคำตอบที่ทำเอง · `p_guess` 0.2 และ `p_slip` 0.1 อยู่ในขอบที่งานต้นฉบับใช้กันโมเดลเพี้ยน · เกณฑ์ผ่าน 0.95 เป็นค่าที่ระบบ BKT ส่วนใหญ่ใช้ · ด้วยค่าปัจจุบัน ตอบถูก 3 ข้อติดได้ 0.986 ซึ่งตรงกับเกณฑ์ "ถูก 3 ข้อติด" ของ ASSISTments

**ทำไมไม่ใช้โมเดลที่แม่นกว่า:** Gervet et al. (2020) เทียบบน 9 datasets พบว่า logistic regression ชนะใน data ขนาดกลาง และ Deep Knowledge Tracing ชนะใน data ใหญ่ โดย BKT แพ้ทั้งสองแบบ · แต่ MVP ยังไม่มีข้อมูลให้ fit และต้องอธิบายให้ผู้เรียนเห็นได้ว่าทำไมระดับเปลี่ยน · Pelánek (2017) สรุปว่าไม่มีโมเดลที่ดีที่สุดทุกกรณี ต้องเลือกตามบริบท · Khajah et al. (2016) แสดงว่า BKT ที่ขยายเพิ่มทำได้ใกล้ DKT จึงยังมีทางพัฒนาต่อโดยไม่ต้องทิ้ง

**ข้อจำกัดที่เจอเองและแก้แล้ว (learning-model v1.2):** BKT ไม่รู้ความยากของโจทย์ · ตอบถูกโจทย์ง่าย 3 ข้อก็ถึง 0.986 ทั้งที่ยังไม่เคยเจอโจทย์ระดับข้อสอบ · ทีมจึงเพิ่ม **ระดับความยากเป้า** ตามดาวของหัวข้อ (★★★ ต้องทำถูกเองที่ระดับข้อสอบ) และ **เพดาน mastery** ตามระดับยากสุดที่ทำถูก ยังขาด 1 ขั้นเพดานอยู่ที่ (0.5 + 0.95) ÷ 2 = 0.725 · ตัวเลขเพดานคำนวณจากค่าที่มีอยู่ ไม่ได้ตั้งเพิ่ม · ทางเลือกที่จะเทียบหลัง Alpha คือ BKT ที่มี guess/slip ต่อระดับความยาก (KT-IDEM, Pardos & Heffernan 2011) และ Elo (Pelánek 2016) · ยังไม่ได้เปิดอ่านต้นฉบับทั้ง 2 งาน

### 4.3 เมื่อไหร่นับว่า "ผ่าน"

- **รองรับ:** meta-analysis 108 การทดลองของ Kulik, Kulik & Bangert-Drowns (1990) พบว่า mastery learning ทำให้คะแนนสอบดีขึ้น และได้ผลมากกับนักเรียนที่อ่อน แต่ใช้เวลามากขึ้น · แอปมีวันสอบเป็นเส้นตาย planner จึงลดระดับเป้าของหัวข้อ ★★ เมื่อเวลาไม่พอ
- **ท้าทาย:** Pelánek (2018) ชี้ว่าค่า 0.95 แปลว่า "มั่นใจ 95% ว่ารู้แล้ว" ได้เฉพาะเมื่อหน่วยความรู้ละเอียด · ตอนนี้ BKT คิดระดับ **หัวข้อ** ซึ่งหยาบ แม้เงื่อนไขผ่านจะตรวจระดับ skill (ทุก skill ที่ออกสอบต้องทำถูกเองอย่างน้อย 1 ครั้ง) · Zhang et al. (2025) พบว่าผู้เรียนที่ถึง ≥ 0.98 เรียนบทถัดไปได้ดีกว่า (เป็นความสัมพันธ์ ไม่ใช่เหตุและผล)

### 4.4 ให้โจทย์ก่อน และสอนทันทีเมื่อผิด

ห้องติวเริ่มทุกหัวข้อด้วยโจทย์ (Probe) แล้วค่อยสอน แทนการให้อ่านชีท · เมื่อผิด ชี้บรรทัดแรกที่ผิดและอธิบายทันที แล้วให้โจทย์แบบเดียวกันเพื่อวัดความเข้าใจ แทนการถามว่า "เข้าใจไหม"

- Dunlosky et al. (2013) ประเมินเทคนิคการเรียน 10 แบบ · มีเพียง practice testing และ distributed practice ที่ได้ "high utility" · การอ่านซ้ำและขีดเส้นใต้ได้ "low"
- Richland, Kornell & Kao (2009): ทำแบบทดสอบก่อนเรียนช่วยให้จำดีขึ้นแม้จะตอบผิด (pretesting effect) · รองรับ Probe
- Hattie & Timperley (2007) และ Shute (2008): feedback ที่ดีต้องเจาะจงและทันเวลา · รองรับการชี้บรรทัดแรกที่ผิด (AM-05) · แต่ยังไม่เจองานที่ตอบตรงว่าการไม่ให้ hint ดีกว่าการให้ hint
- VanLehn (2011) พบว่าระบบที่ตรวจทีละขั้นได้ผลใกล้ครูตัวต่อตัว · checker ของเราตรวจทีละบรรทัดจึงเป็นแบบนี้ · ยังไม่ได้เปิดต้นฉบับ จึงไม่อ้างตัวเลข effect size

### 4.5 ทวนตามรอบ และพักเมื่อติด

- **Spaced review:** Cepeda et al. (2006) รวม 317 การทดลอง และ Cepeda et al. (2008) พบว่าระยะห่างที่ดีที่สุดระหว่างการทวนยาวขึ้นตามเวลาที่ต้องจำ · สำหรับช่วงสั้นประมาณ 20% ของเวลาที่เหลือ · แอปจึงไม่ตั้งรอบทวนที่ห่างเกิน 20% ของวันที่เหลือก่อนสอบ และเพิ่มระยะห่างตามค่าเริ่มต้นของ SM-2 (1 วัน แล้วคูณ 2.5)
- **Park:** Beck & Gong (2013) นิยาม wheel-spinning ว่าทำเกิน 10 ข้อแล้วยังไม่ถูก 3 ข้อติด · แอปพัก skill ที่ทำครบ 10 ข้อในวันเดียวแล้วยังไม่ผ่าน แล้วพาไปทวน prerequisite หรือกลับมาวันหลัง
- **ลำดับหัวข้อ:** Knowledge Space Theory (Doignon & Falmagne 1985 ซึ่งยังไม่ได้เปิดต้นฉบับ · Falmagne & Doignon 2011) อธิบายความรู้เป็นโครงสร้างของ prerequisite ซึ่งเป็นฐานของ ALEKS · Doroudi, Aleven & Brunskill (2019) review การใช้ reinforcement learning จัดลำดับการสอน และพบว่าได้ผลเมื่อถูกจำกัดด้วยทฤษฎีการเรียนรู้ · รองรับ planner แบบกฎที่อธิบายได้ แทนโมเดลที่ต้องใช้ข้อมูลเยอะ

### 4.6 ความพร้อม % และความเสี่ยงที่จะมั่นใจเกิน

ความพร้อม = ค่าเฉลี่ยของ mastery (หลังเพดานความยาก) ถ่วงด้วยสัดส่วนที่หัวข้อออกในข้อสอบเก่า · Bull & Kay (2016) ให้กรอบออกแบบหน้าจอที่ให้ผู้เรียนเห็นสิ่งที่ระบบคิดว่าเขารู้ (open learner model) ซึ่งใช้กับการ์ดความคืบหน้า · แต่ Dunlosky & Rawson (2012) พบว่าผู้เรียนที่ประเมินตัวเองสูงเกินจะหยุดทวนเร็วเกินแล้วผลออกมาแย่ (ยังไม่ได้เปิดต้นฉบับ) · เพดาน mastery ใน 4.2 ส่วนหนึ่งทำเพื่อไม่ให้ความพร้อมสูงเกินจริงตอนที่ยังทำได้แค่โจทย์ง่าย · สูตรนี้ยังไม่เคยเทียบกับคะแนนสอบจริง Feng, Heffernan & Koedinger (2009) เป็นแนวทางสำหรับ validate

### 4.7 ประเด็นที่ยังเปิดอยู่

งานวิจัยท้าทาย design ปัจจุบัน 6 เรื่อง ซึ่งรอข้อมูลจาก Alpha และการคุยกับอาจารย์ที่ปรึกษา · ข้อ 1–5 อยู่ใน agenda ของทีม (`docs/research/agenda-learning-model.md` · ข้อ 1, 2, 4 เป็นวาระที่จะคุย ข้อ 3, 5 อยู่ใน "ยังไม่คุยรอบนี้") · ข้อ 6 มาจาก learning-model §10 และหัวข้อ 4.2

1. BKT ระดับหัวข้อ หรือระดับ skill (Pelánek 2018)
2. BKT หรือ logistic model เมื่อมีข้อมูลแล้ว (Gervet et al. 2020 · Khajah et al. 2016)
3. เกณฑ์ mastery 0.95 หรือสูงกว่า (Zhang et al. 2025)
4. ความพร้อม % ทำให้มั่นใจเกินไหม และ validate กับคะแนนสอบจริงอย่างไร (Dunlosky & Rawson 2012 · Feng et al. 2009)
5. mastery ควรลดลงตามเวลาไหม (Settles & Meeder 2016)
6. เพดานตามความยาก เทียบกับ KT-IDEM และ Elo (หัวข้อ 4.2)

**วิธีพิสูจน์ผลของแอป** (pilot): ใช้ normalized gain ของ Hake (1998) กับ pre/post test · Kulik & Fletcher (2016) รวม 50 การทดลองของ ITS ได้ median 0.66 SD แต่ผลจะใหญ่กว่าเมื่อวัดด้วยข้อสอบที่ทำเอง · ข้อสอบ pre/post ของ pilot จึงต้องออกแบบไม่ให้ผลดูดีเกินจริง
