## 1. สถาปัตยกรรม AI

### 1.1 หลักคิด: code ตัดสินใจ, LLM พูด

ปัญหาหลักของห้องติวที่ใช้ LLM ทั้งหมดคือ ทดสอบไม่ได้และอธิบายไม่ได้ว่าทำไมระบบเลือกสอนหัวข้อนั้นหรือให้คะแนนแบบนั้น "อ่านยัง?" จึงแยกหน้าที่ชัดเจน (ai-orchestration §1.3):

| ส่วน | ใครตัดสิน | ตัวอย่าง |
|---|---|---|
| ลำดับการสอน, หัวข้อถัดไป, ดาวความสำคัญ, ระดับความเข้าใจ (mastery), AI Buddy จะพูดไหม | **code** (Python ที่ test ได้ ใน `apps/api/app/domain/`) | ดาวคิดจากสัดส่วนข้อสอบเก่าที่หัวข้อนั้นออก (§2.3.5) · mastery คิดด้วย BKT (หัวข้อ 4) |
| คำตอบคณิตถูกหรือผิด และผิดตั้งแต่บรรทัดไหน | **SymPy** (math engine) | เทียบทีละบรรทัดว่าเท่ากับบรรทัดก่อนหน้าไหม (หัวข้อ 3 · P2) |
| ผิดแบบไหน, ประโยคที่ใช้อธิบาย, คำพูดของ tutor | **LLM** | `sign` เพราะ −3 กลายเป็น +3 |

code ส่ง **directive** (คำสั่งว่า turn นี้ต้องทำอะไร) ให้ LLM แปลงเป็นคำพูด · LLM ไม่ได้เลือกแผนการสอนเอง จึงไม่หลุดแผนเมื่อบทสนทนายาว และทุกการตัดสินใจมี unit test รองรับ

### 1.2 AI ไม่เขียน database เอง

LLM คืนผลเป็น structured output (JSON ตาม Pydantic schema) หรือ action จาก whitelist เท่านั้น เช่น `set_importance`, `exclude` ตอนผู้ใช้แก้ขอบเขต · code ตรวจว่า id มีจริง ค่าอยู่ในช่วง และ op อยู่ใน whitelist ก่อน apply (§2.3.6) · ป้องกันทั้ง hallucination และ prompt injection ที่พยายามให้ AI แก้ข้อมูลเอง

### 1.3 AI Gateway เดียว

ทุก AI call ในระบบผ่านฟังก์ชันเดียว `ai.call(purpose, input, schema)` (`apps/api/app/ai/gateway.py` · AI-01) ซึ่งทำ 5 อย่าง:

1. โหลด prompt ตาม version ที่ระบุใน `config/ai.yaml`
2. เลือก model ตาม **tier** ของงาน (small, mid, main, vision, embed) · เปลี่ยน provider ได้โดยแก้ config ไม่ต้องแก้ code (AI-02)
3. ตรวจ output กับ schema และ retry พร้อมแนบ error เมื่อไม่ผ่าน (AI-05)
4. retry เมื่อ provider ล่มหรือ timeout หลัง backoff
5. บันทึก token, latency และสถานะของทุก call (AI-04)

ผลที่ได้: test ทั้งหมดใช้ **fake provider** ที่ตอบคงที่ (AI-03) จึงรันได้ใน CI โดยไม่มีค่าใช้จ่าย · ส่วนการวัดกับ model จริงแยกเป็น eval (หัวข้อ 2)

model ที่เลือกมาจากผล PoC (`config/ai.yaml` 1.3):

| tier | model | ที่มา |
|---|---|---|
| vision (อ่านลายมือ) | `gemini-3.5-flash-lite` | P1: อ่านถูก 95.2% ของบรรทัด |
| mid (สกัดหัวข้อ, ตรวจคำตอบ) | `gemini-3.5-flash` | P3: flash-lite หยาบเกินสำหรับสกัดหัวข้อ |
| embed (ค้นเนื้อหา) | `gemini-embedding-2` ที่ 768 มิติ | P3b: หาหน้าคำตอบเจอใน 4 อันดับแรก 19/20 |

ฉบับ lite ที่ใช้ในเทอม 1 ยังไม่มี fallback ไป provider ที่สอง, circuit breaker และการเขียน log ลงตาราง `ai_calls` (แผนของเทอม 2)

### 1.4 Prompt เป็นไฟล์ที่มี version

prompt ทุกตัวอยู่ใน `prompts/<purpose>/v<n>.md` ไม่ใช่ string ในโค้ด · แก้ prompt = สร้าง version ใหม่ ไม่แก้ไฟล์เดิม แล้วรัน eval เทียบกับ version เดิมใน PR เดียวกัน (`prompts/README.md`) · ทำให้ย้อนดูได้ว่าตัวเลขใน report วัดจาก prompt ไหน

**ข้อมูลของผู้ใช้เป็นข้อมูล ไม่ใช่คำสั่ง:** เนื้อหาจากชีท ข้อสอบ และคำตอบของนักศึกษาอยู่ใน `<document>…</document>` เสมอ และ prompt บอก model ว่าข้อความในนั้นห้ามทำตาม · มี test ยืนยันว่าข้อความอย่าง "ignore previous instructions" ในคำตอบอยู่ใน `<document>` เท่านั้น (`test_check_answer_pipeline.py`)

### 1.5 ตัวอย่าง: ตรวจคำตอบ 1 ข้อ

ตัวอย่างนี้แสดงหลักทั้งหมดข้างบนในงานเดียว (ai-orchestration §2.4 · PR #68, #75, #80)

โจทย์: หา d/dx (x² sin x) · นักศึกษาเขียน 3 บรรทัด และบรรทัดที่ 3 ผิดเครื่องหมาย

1. **SymPy** คำนวณค่าของทุกบรรทัด (รวมการหาอนุพันธ์) แล้วเทียบกับบรรทัดก่อนหน้า → บรรทัด 3 ไม่เท่ากับบรรทัด 2 · คำตอบสุดท้ายไม่เท่าเฉลย
2. **code** ลองกลับเครื่องหมายทีละพจน์ในบรรทัด 3 แล้วพบว่าถูก → ส่ง hint `sign_flip_detected: line 3`
3. **LLM** (`check_answer`) ได้ผล SymPy เป็นประโยคสั้น + hint แล้วตอบว่า error type คือ `sign` พร้อมหลักฐานภาษาไทย 1 ประโยค
4. **merge rules** (code) รวมผล: ถูกหรือผิดและบรรทัดที่ผิดมาจาก SymPy · ประเภทความผิดมาจาก LLM · ถ้า LLM บอกว่าถูกแต่ SymPy บอกว่าผิด เชื่อ SymPy และบันทึกว่าขัดกัน
5. ผลลัพธ์ "ยังไม่ถูก · บรรทัด 3" แสดงในห้องติว (PR #78) และ tutor อธิบายวิธีแก้ทันที

ถ้า SymPy ตรวจคำตอบนั้นไม่ได้ (เช่น implicit differentiation หรือใช้เวลาเกิน 2 วินาที) LLM จะตัดสินแทนพร้อมค่า confidence และผู้ใช้แย้งผลได้ (AM-12)
