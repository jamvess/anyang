## สรุปการปรับปรุงจากข้อเสนอโครงงาน

หลังการนำเสนอข้อเสนอโครงงาน ทีมได้ปรับการออกแบบและขอบเขตของโครงงานตามข้อเสนอแนะของคณะกรรมการ และตามสิ่งที่พบระหว่างการทำ PoC หัวข้อนี้สรุปการปรับปรุงทั้งสองส่วน พร้อมระบุหัวข้อในรายงานที่อธิบายรายละเอียด

### 1. การดำเนินการตามข้อเสนอแนะของคณะกรรมการ

คณะกรรมการให้ข้อเสนอแนะ 2 ประเด็น ประเด็นแรก การออกแบบลำดับการเรียนรู้ (learning path) และการติดตามความก้าวหน้า (progress tracking) ต้องมีหลักการรองรับ และต้องแสดงให้เห็นว่าอัลกอริทึมที่ใช้มีความน่าเชื่อถือ ประเด็นที่สอง ข้อเสนอโครงงานยังไม่แสดงให้เห็นว่าทีมออกแบบและพัฒนาส่วนใดด้วยตนเอง ทำให้งานดูเป็นเพียงการเรียกใช้ API ของ AI ทีมต้องแสดงการออกแบบระบบ pipeline ฐานข้อมูล RAG และการทดสอบ เพื่อให้เห็นว่างานมีความซับซ้อนเหมาะสมกับโครงงานของนักศึกษาสามคน ตารางที่ ก สรุปสิ่งที่ทีมดำเนินการในแต่ละประเด็น

ตารางที่ ก การดำเนินการตามข้อเสนอแนะของคณะกรรมการ

| ข้อเสนอแนะ | สิ่งที่ทีมดำเนินการ | หัวข้อในรายงาน |
|---|---|---|
| **1. learning path และ progress tracking ต้องมีหลักการรองรับและน่าเชื่อถือ** | | |
| 1.1 หลักการของ learning path | ออกแบบลำดับการติวเป็นขั้นตอนที่โปรแกรมกำหนด ได้แก่ วัดความรู้เดิม สอน และยืนยันความเข้าใจ (Probe, Teach, Verify) และเลือกหัวข้อถัดไปจากความสำคัญ ระดับความเข้าใจ และเวลาที่เหลือก่อนสอบ โดยอ้างอิงงานวิจัยด้านการฝึกดึงความรู้ การทบทวนแบบเว้นระยะ และการเรียนแบบรอบรู้ (mastery learning) | 2.1, 2.2.4, 2.6, 3.6 |
| 1.2 หลักการของ progress tracking | ประเมินความเข้าใจรายหัวข้อด้วย Bayesian Knowledge Tracing ซึ่งเป็น model ที่ตีความค่าได้และใช้ข้อมูลน้อย กำหนดเพดานความเข้าใจตามระดับความยากของโจทย์ที่ผู้เรียนทำถูกได้เอง และคำนวณความพร้อมสอบโดยถ่วงน้ำหนักด้วยความสำคัญของหัวข้อ | 2.2, 2.6, 3.7 |
| 1.3 ความน่าเชื่อถือของอัลกอริทึม | ให้โปรแกรมเป็นผู้ตัดสินทุกขั้นของ learning model แทน LLM ทำให้ผลเหมือนเดิมทุกครั้งที่ข้อมูลเหมือนเดิม รวบรวม parameter ทั้งหมดไว้ในไฟล์ config เดียวพร้อมระบุที่มา ทดสอบทุกเกณฑ์ที่ค่าขอบ และวางแผนพิสูจน์กับผู้เรียนจริงด้วยการ calibrate ค่า การเปรียบเทียบความพร้อมสอบกับคะแนนสอบจริง และแบบทดสอบก่อนและหลังใช้ระบบ | 3.7, 4.4, 5.2 |
| **2. แสดงสิ่งที่ทีมออกแบบและพัฒนาเอง และความซับซ้อนของงาน** | | |
| 2.1 การแบ่งหน้าที่ระหว่างโปรแกรมกับ AI | กำหนดหลักการว่าโปรแกรมเป็นผู้ตัดสินใจ และ LLM ทำหน้าที่ด้านภาษาเท่านั้น พร้อมแผนภาพที่แสดงว่าการสนทนาหนึ่งรอบในห้องติวผ่านส่วนใดที่เป็นโปรแกรมและส่วนใดที่เป็น LLM | 3.2 (รูปที่ 3.1) |
| 2.2 Pipeline | ออกแบบและพัฒนา pipeline นำเข้าเอกสาร 7 ขั้น ตั้งแต่จำแนกไฟล์จนถึงจัดเก็บเนื้อหาพร้อม embedding และ pipeline ตรวจคำตอบ ตั้งแต่อ่านลายมือ ตรวจทีละบรรทัดด้วย SymPy จำแนกประเภทความผิด จนถึงรวมผล | 3.5, 3.8 |
| 2.3 ส่วนกลางสำหรับเรียกใช้ AI | พัฒนา AI gateway ที่ทุกการเรียก AI ต้องผ่าน ทำหน้าที่เลือก model ตามงาน ใช้ prompt ที่มีหมายเลขรุ่น ตรวจรูปแบบผลลัพธ์และขอใหม่เมื่อไม่ถูกต้อง แยกข้อมูลผู้ใช้ออกจากคำสั่ง และบันทึกเวลาและค่าใช้จ่ายของทุกการเรียก | 3.3 |
| 2.4 ฐานข้อมูล | ออกแบบฐานข้อมูลแบบ multi-tenant 28 ตาราง ทุกตารางบังคับแยกข้อมูลด้วย Row-Level Security และมีการทดสอบการแยกข้อมูลอัตโนมัติ | 3.9 |
| 2.5 RAG (Retrieval-Augmented Generation) | แบ่งเอกสารเป็นส่วนย่อยพร้อม embedding และวัดความแม่นยำของ retrieval ปัจจุบันห้องติวอ้างอิงเนื้อหาจากหน้าเอกสารที่เป็นที่มาของหัวข้อ ส่วน vector search ใช้สำหรับคำถามนอกขอบเขตในขั้นถัดไป ❓ | 2.3.3, 3.5 |
| 2.6 การทดสอบและการประเมินผล | PoC 6 ชุดด้วยชุดข้อมูลที่มีเฉลยและเกณฑ์ที่กำหนดไว้ก่อนวัด และ automated test มากกว่า 2,600 test case ซึ่งทำงานทุกครั้งที่มีการแก้ไขโค้ด | 4.1, 4.4 |
